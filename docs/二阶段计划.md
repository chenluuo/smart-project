# 二阶段计划：仓储与采购意向系统

> 状态：**定稿（取代 `二阶段计划_初版.md` 与 `二阶段开发差量清单.md`，旧文件已取缔）**
> 定位：智慧农业"端-智-云"系统业务扩展 —— 本系统是**供应链最开端**（农场为源头供给方）
> 原则：以 Go 端为基准、能复用就复用；前端只依赖 Go API（Go 是唯一网关）；Agent 不参与交易写路径
> 拆分维度：后端（Go）/ 前端 / Agent 三部分，任务分配由组长另行拆分

> 实际状态（2026-08-30）：仓储后端已经落地；采购意向/订单、CUSTOMER 自助注册、前端仓储页面和 Agent 接入仍待实现。当前仓储 API 仅允许 `WAREHOUSE_MANAGER / SYSTEM_ADMIN`，其他角色均不得访问。

---

## 一、业务规则（定稿，实现必须遵守）

1. **供应链最开端**：顾客（下游商家）发的是**采购意向**而非确定订单；意向审批通过后进入生产（衔接现有灌溉系统），收获后再**面谈成交**
2. **全系统无价格**：意向、成交、物料、订单、流水全链路不出现任何价格字段
3. **成交后系统只做两件事**：按实际成交数量**扣库存** + **结束订单（软删除）**；无后续履约、无收款
4. **待交易（TRADING）中间态**：批准即占用可售数量，防止"一批作物被误认为能满足两个商家"
5. **管理员面板直接看可用数量**，不做满足度（充足/部分/不足）计算

## 二、后端（Go）实现方案

| 角色 | 能力 | 来源 |
|---|---|---|
| CUSTOMER 顾客 | 自助注册、发采购意向、查看/取消自己的意向 | **新增** |
| WAREHOUSE_MANAGER 仓库管理员 | **管理仓库与订单**：物料/仓库/库存/流水管理 + 意向审批/成交/关闭 | **新增** |

| ADMIN（SYSTEM_ADMIN） | 全部权限（含仓库与订单） | 现有 |
| TECHNICIAN | 只负责技术与设备相关能力，不访问仓储域 | 现有 |

- 当前迁移已新增 `WAREHOUSE_MANAGER`；`CUSTOMER` 随订单/注册模块后续新增。
- 当前自助注册仍固定绑定 `FARMER`；顾客/农户身份选择尚未实现。
- 当前管理接口只支持查询用户，尚未提供创建账号或分配角色接口；仓库管理员需由部署管理员写入角色关系，后续再补 SYSTEM_ADMIN 管理入口。

### 2.2 数据模型（MySQL 6 张表，沿用现有表规范：主键/时间戳/软删除 `status=DELETED`）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `materials` | name, category(作物), unit, spec| 农产品主数据 |
| `warehouses` | name, location | 成品仓主数据 |
| `stocks` | (warehouse_id, material_id) 联合唯一, quantity | 库存，唯一约束防同物料重复行 |
| `stock_records` | type(IN/OUT), quantity, ref_type/ref_id(挂订单), plot_id(来源地块,可空), operator, remark | 出入库流水，恒等式 `期初+ΣIN−ΣOUT=当前` 可验账 |
| `order_headers` | order_no(唯一,Go生成如 `INT-20260830-001`), status, customer_id, expected_time(期望时间,可空), remark | 意向单主表 |
| `order_items` | order_id, material_id, quantity(意向数量,成交时更新为实成交量) | 意向明细，支持一个意向多品种 |

- 意向单软删除：成交（CONFIRMED）后 `status=DELETED`，从列表消失但 DB 行 + 流水保留可追溯
- `order_no` 由 Go 生成（日期+当日序号），唯一索引兜底

### 2.3 状态机与库存占用（核心逻辑）

```
PENDING(待审批) ──审批通过──▶ APPROVED(已批准) ──进入待交易──▶ TRADING(待交易)
      │                             └── 审批拒绝 ──▶ REJECTED(终态)
      ▼
  TRADING ──面谈成交(按实际数量)──▶ CONFIRMED（扣库存+释放多余占用+流水OUT+软删，终态）
      └── 谈崩/放弃 ──▶ CLOSED（释放全部占用，终态）
```

- 状态枚举：`PENDING / APPROVED / TRADING / CONFIRMED / CLOSED / REJECTED`（字符串存储）
- **可售数量公式**（防"一批货满足两家"的核心）：

```
available(material) = Σ(stocks.quantity) − Σ(TRADING 状态下 order_items.quantity，按物料聚合)
```

- 占用是**虚拟占用**：只靠状态聚合现算，不锁库存行、不写流水、无额外表
- 发意向校验：意向数量 ≤ 可售，否则拒绝（前端同步提示）
- **成交事务**（`confirm`，管理员）：同事务内 行锁(`SELECT ... FOR UPDATE`) → 校验库存充足 → 按实际成交数量扣库存 → 写流水 OUT（挂订单号）→ 释放多余占用（意向 500 成交 400 → 扣 400、释放 100）→ 订单软删除
- **关闭**（`close`，谈崩）：释放全部占用，作物回到可售，不产生流水
- **取消**（`cancel`）：仅 PENDING 状态可取消，顾客/管理员均可
- 多品种意向：占用/释放按 `(material_id)` 逐行聚合处理

### 2.4 API 清单（挂在 Go 网关 `/api/v1/...`，权限中间件沿用现有）

| 方法/路径 | 说明 | 权限 |
|---|---|---|
| `POST /auth/register` | 自助注册（身份可选：顾客/农户，绑定 CUSTOMER/FARMER） | 公开 |
| `GET /market/materials` | 交易市场在售商品（含可售数量） | 全员 |
| `POST /orders` | 发采购意向（品名+意向数量+期望时间） | CUSTOMER |
| `GET /orders` | 意向列表（可按状态过滤） | FARMER/ADMIN/WAREHOUSE_MANAGER（全部）；CUSTOMER（仅自己的） |
| `GET /orders/{id}` | 意向详情（含明细、可用数量） | FARMER/ADMIN/WAREHOUSE_MANAGER（全部）；CUSTOMER（仅自己的） |
| `POST /orders/{id}/review` | 审批（body: `action=approve\|reject`，仅 PENDING）→ APPROVED(并进入 TRADING)/REJECTED | ADMIN/WAREHOUSE_MANAGER |
| `POST /orders/{id}/terminate` | 终止（body: `action=cancel\|close`）：PENDING 取消 / TRADING 谈崩关闭（释放占用） | cancel: CUSTOMER(本人)/ADMIN/WAREHOUSE_MANAGER；close: ADMIN/WAREHOUSE_MANAGER |
| `POST /orders/{id}/confirm` | 面谈成交（带实际成交数量）→ 扣库存+软删 | ADMIN/WAREHOUSE_MANAGER |
| `POST /stocks/inbound` | 仓库管理员根据收获信息记录入库（物料/数量/来源地块） | ADMIN/WAREHOUSE_MANAGER |
| `GET /stocks` | 库存查询（总量/已占用/可用） | ADMIN/WAREHOUSE_MANAGER |
| `GET /stock-records` | 出入库流水（按物料/仓库/时间过滤） | ADMIN/WAREHOUSE_MANAGER |
| `GET/POST/PUT/DELETE /materials` `/warehouses` | 仓储主数据查询与管理 | ADMIN/WAREHOUSE_MANAGER |

> **Agent 取数说明**：意向列表/详情的权限由后续订单模块单独定义。仓储接口不向 FARMER、FARM_ADMIN、TECHNICIAN、CUSTOMER 或 Agent 开放；如 Agent 后续确需仓储数据，应新增受控内部接口或使用 SYSTEM_ADMIN/WAREHOUSE_MANAGER 服务身份，不能绕过仓储角色边界。

### 2.5 事务与并发控制

- 成交/入库全部用 MySQL 事务 + 行锁，杜绝超卖与部分扣减
- 状态流转做前置校验（如 CONFIRMED 只允许从 TRADING 进入），非法流转返回冲突
- 成交接口带实际成交数量入参，与意向数量解耦（面谈可谈出不同量）

### 2.6 实现位置建议（对齐现有目录结构）

- `backend/internal/trade/`（新域包）：`model.go`（6 表模型）+ `repository.go` + `service.go`（状态机/占用/成交事务）
- `backend/internal/http/trade.go`：handler + 路由注册（router.go 新增 `registerTradeRoutes`）；订单接口按角色和归属单独鉴权。仓储接口统一限定为 SYSTEM_ADMIN/WAREHOUSE_MANAGER，不与订单市场的公开读取权限混用。
- `backend/internal/identity/`：CUSTOMER、WAREHOUSE_MANAGER 角色支持；角色中间件白名单按接口配置（订单/仓库域接口对 WAREHOUSE_MANAGER 放行）
- 复用：现有分页/响应封装/角色中间件/软删除过滤模式

## 四、Agent 实现方案（职责细化）

### 4.1 定位与边界

- Agent 是"智"层，核心价值是**农事决策辅助**；交易/库存写操作（发意向、审批、成交、入库）仍全在 Go，Agent 不参与写路径
- Agent 新增两项明确职责：**① 读取订单内容 → 种植建议（取代订单文档入知识库）② 收获入库记录**

### 4.2 职责一：读取订单内容 → 种植建议

**取代旧路径**：
- 旧：订单/采购计划以文档形式上知识库（docling 解析 → Milvus RAG），问答时检索文档——文档滞后、与订单实时状态脱节、同一份数据维护两份
- 新：Agent 通过**只读工具实时读取订单（意向）内容**，直接作为决策输入，订单文档不再上传

**实现**：
1. 新增 Agent 工具 `get_order_intents`：调 Go `GET /orders`（支持按状态 APPROVED/TRADING 过滤），返回意向清单（物料、意向数量、期望时间）
2. 组装种植建议上下文：意向内容 + 作物知识 RAG 检索（现有）+ 地块/设备现状（复用现有 plot/telemetry 工具）
3. 输出建议：基于意向数量推算种植面积/预计产量/茬口安排（例：意向番茄 500kg → 建议种植 X 亩、预计收获 Y kg）
4. 触发方式：用户对话（如"这批意向怎么安排种植？"）；可选：审批通过后 Agent 主动推送建议

**对知识库的影响**：订单文档不再上传；知识库回归纯作物/种植知识（现有番茄/大白菜/萝卜/胡萝卜参数文档等）

### 4.3 职责二：收获入库记录

- 收获入库（`POST /stocks/inbound`）成功后，Agent **记录本次收获**（写入长期记忆），供后续问答与决策引用
- 记录内容：plot_id（来源地块）、物料、数量、时间
- 实现（推荐复用现有事件链路，Go 最小改动）：
  1. Go 入库成功 → outbox 写收获事件（复用现有 `KNOWLEDGE_DOCUMENT_*` 模式，新增 `STOCK_INBOUND_*` 类型）→ Agent 经 `/internal/.../notify` 接收 → 写记忆（Milvus memory collection，user_id 隔离）
  2. 兜底：Agent 工具 `get_stock_records`（调 Go `GET /stock-records`）问答时按需读取
- 后续价值：问答"最近收了什么 / 3 号地块产量如何"，Agent 能直接回答，不用翻文档

### 4.4 Agent 新增工具清单

| 工具 | 数据源（Go 接口） | 用途 |
|---|---|---|
| `get_order_intents` | `GET /orders`（FARMER/ADMIN 身份 JWT + X-Internal-Key，状态过滤） | 读意向内容 → 种植建议 |
| `get_stock_records` | 受控内部接口或仓储服务身份（后续设计） | 收获/出库流水查询，不使用 FARMER/TECHNICIAN 身份绕过仓储权限 |
| （事件侧）收获记录 | outbox `STOCK_INBOUND_*` → notify | 入库后写记忆 |

### 4.5 与现有 Agent 能力的关系

- 复用：RAG 知识检索、长期记忆（Milvus）、会话状态机、告警分析、灌溉决策链路
- 新增工具与现有工具清单并列注册（`agent/tool-service/tools/impl.py` + `register_all()`）

## 五、演示数据与验收

- **演示数据**：3~4 个农产品物料、1 个成品仓、仓库管理员根据农场收获信息登记两笔入库、一个顾客发意向 → 仓库管理员审批 → 另一顾客发同物料意向被"可用数量"拦截 → 成交扣库存 → 流水可验账
- **验收标准**：
  1. 顾客自助注册后能发意向，仓库管理员/系统管理员能看到全部意向及对应物料可用数量
  2. 两个商家先后对同一批作物发意向，第二个因可用不足被拦截（防误满足）
  3. 成交后：库存按实成交量扣减、流水 OUT 挂订单号、订单从列表消失（DB 可追溯）
  4. 谈崩关闭后：占用释放、可售恢复
  5. 全链路无价格字段
  6. 仓库管理员账号登录进入管理面板，仅见"仓库管理 + 订单管理"两页，可完成审批/成交/入库；系统管理员可见全部页面
  7. 注册页可选身份（顾客/农户）；顾客登录自动进入顾客端页面（交易市场/我的意向），农户登录进入现有移动端，管理员类进入管理面板
  8. Agent 能读取意向订单内容并给出种植建议（订单文档不再上知识库）；收获入库后 Agent 能回答"最近收了什么/某地块产量"
